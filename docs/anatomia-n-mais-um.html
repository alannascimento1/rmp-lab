Laboratório Profiler

Anatomia de um N+1

Como ler o painel do rack-mini-profiler usando duas medições reais da mesma página: uma com 121 consultas, outra com 4.

Baseado no rmp-lab, um app Rails lento de propósito. Toda afirmação numérica deste artigo tem prova: as duas medições estão congeladas em HTML no repositório e cada seção aponta o arquivo de código correspondente.

O experimento

O rack-mini-profiler é uma gem que fica no caminho de toda requisição de um app Rails e desenha, na própria página, onde o tempo foi gasto. Para estudar o painel dela, o laboratório serve a mesma lista — 30 posts, com autor e comentários, sobre 40 mil posts e 80 mil comentários — por dois controllers:

  • Lab::Posts::SlowController — carrega só os posts: Post.recent.limit(30) 129,6 ms · 121 sql
  • Lab::Posts::FastController — a mesma linha, com .includes(:user, comments: :user) 21,6 ms · 4 sql

Provas: medição slow (129,6 ms) · medição fast (21,6 ms) — páginas geradas pelo botão share do próprio profiler, guardadas nesta mesma pasta.

As colunas do painel

A visão-resumo tem uma linha por etapa do atendimento — o servidor recebendo a requisição (GET), a action rodando, a view sendo desenhada — e as etapas são caixas uma dentro da outra. As colunas medem cada caixa:

ColunaPergunta que responde
EVENTO que o servidor estava fazendo?
WITH CHILDRENQuanto durou no relógio, do início ao fim, contando tudo que rodou dentro?
DURATIONQuanto sobrou para a própria etapa, descontando as linhas de baixo?
FROM STARTQuando começou, contado da chegada da requisição?
QUERY TIMEQuantas consultas rodaram ali, e quanto custaram?

Definições originais, no código-fonte da gem (v5.0.0, a versão usada aqui) — os mesmos textos aparecem como tooltip ao passar o mouse nas colunas do painel: duration — “duration of this step without any children's durations” · with children — “duration of this step and its children” · from start — “time elapsed since profiling started” · query time — “aggregate duration of all queries in this step (excludes children)”

Na medição slow, a conta fecha assim:

Etapawith childrendurationfrom start
GET /lab/posts/slow129,63,8+0,0
  Executing: slow#index125,82,2+3,0
    Rendering: slow/index123,6123,6+4,4

Duration é uma subtração. A requisição inteira levou 129,6 ms; a view explica 123,6 e a action 2,2 — sobram 3,8 ms, que é o trabalho do próprio framework (receber o pedido, resolver a rota, enviar a resposta). Somando a coluna duration, 3,8 + 2,2 + 123,6 = 129,6: cada milissegundo aparece em exatamente uma linha. A view tem os dois números iguais porque não há nada dentro dela. E from start é a linha do tempo: a action entrou a +3,0, a view a +4,4.

O sintoma: 121 consultas na view

O contador de SQL da medição slow marca 121 (33 cached) — e 120 delas estão penduradas na linha do Rendering, não na da action. Não é acaso: o Active Record é preguiçoso. Post.recent.limit(30) no controller só monta a consulta; quem dispara é a view, quando itera a lista. A primeira consulta da medição prova isso — o backtrace do SELECT posts aponta para a view, não para o controller:

SELECT "posts".* FROM "posts" ORDER BY "posts"."published_at" DESC LIMIT 30
→ app/views/lab/posts/slow/index.html.erb:10

Dali em diante, o ciclo se repete por post: o card lê post.user.name (linha 5 da partial), post.comments (linha 8) e o autor de cada comentário (linha 8, dentro de um map). Três origens de consulta, trinta vezes:

SELECT "users".*    WHERE id = ?   → _post_card.html.erb:5   (autor do post)
SELECT "comments".* WHERE post_id = ? LIMIT 2 → _post_card.html.erb:8
SELECT "users".*    WHERE id = ?   → _post_card.html.erb:8 em Array#map
[CACHE] SELECT "users".* WHERE id = ?  ← repetição respondida da memória

Prova: abra a medição slow, clique em 121 sql e confira os backtraces — todos apontam para _post_card.html.erb, linhas 5 e 8.

Duas leituras finas dessa lista:

  • [CACHE] marca consultas idênticas que o query cache do Active Record respondeu sem ir ao banco — as 33 do resumo. Elas amenizam o custo, mas continuam sendo 33 idas e voltas em Ruby.
  • O banco não é o vilão. As 121 consultas custaram 13,0 ms — 10% dos 129,6 totais. O caro do N+1 é o Ruby montar, executar e processar 121 chamadas para desenhar 30 cards.

A correção: uma linha

O controller corrigido difere em uma chamada — .includes(:user, comments: :user) — que pede ao Active Record para carregar autores e comentários junto. A medição fast mostra o resultado: 4 consultas, nenhuma repetida:

msConsulta
7,1SELECT posts ORDER BY published_at DESC LIMIT 30
0,4SELECT users WHERE id IN (30 ids de uma vez)
0,6SELECT comments WHERE post_id IN (...)
0,2SELECT users WHERE id IN (autores dos comentários)

O WHERE id IN (…) é a assinatura do eager loading: uma consulta por associação, em vez de uma por registro. A view é a mesma; o Rendering caiu de 123,6 para 16,8 ms porque o que sumiu foram as idas ao banco dentro dele. Total: 129,6 ms → 21,6 ms.

Prova: medição fast — os 4 backtraces apontam para a linha 9 de fast/index.html.erb, o render da collection.

Cuidado com o percentual

A slow marca 10% in sql e a fast 38% — parece que a corrigida usa mais banco, mas é o contrário: 8,3 ms contra 13,0. O percentual é fatia do total, e o total encolheu de 129,6 para 21,6 ms. Para comparar páginas, use milissegundos; o percentual só diz onde o tempo daquela requisição está.

O lado do navegador

A segunda tabela do painel é medida no browser, com o mesmo cronômetro. Comparando as duas medições:

Evento (from start)slowfast
Resposta chegou (Response)+136+27
DOM pronto (domInteractive)+150+42
Página carregada (Load Event)+156+56

O servidor respondeu em 129,6 ms, mas quem usa só viu a página completa a +156 — rede e o trabalho do navegador (parse do HTML, CSS, layout) vêm depois. O tempo que o usuário sente é sempre maior que o tempo do servidor, e o painel mostra os dois na mesma régua.

O que fica

  • Duration responde "quem é o culpado" — o maior número da coluna é onde o código queima tempo. With children responde "quanto durou".
  • N+1 aparece embaixo do render, porque o Active Record só executa quando a view usa os dados — e o backtrace entrega a linha exata.
  • Consultas idênticas empilhadas (e [CACHE]) são o sintoma; includes com WHERE IN é a cura — 121 → 4 consultas com uma linha.
  • Percentual de SQL não compara páginas; milissegundos comparam.

Referências técnicas

  • Colunas do painel — template da interface da gem, com as definições em tooltip: includes.tmpl, linhas 179–199.
  • Etiqueta [CACHE] — a gem recebe a marca de consulta cacheada do Rails e renderiza o selo: timer_struct/sql.rb#L13 (parâmetro cached). O mecanismo por trás é o SQL cache do Active Record: Rails Guides, “SQL Caching”.
  • Por que a etiqueta DUPLICATE não aparece — o campo existe no template (includes.tmpl#L231), mas nasce false e nenhum código o ativa nesta versão: timer_struct/sql.rb#L53. A repetição se identifica pelos selects empilhados e pelo contador de cached.
  • Carregamento preguiçoso e includes — Rails Guides, “Eager Loading Associations” (o problema N+1 é o exemplo de abertura do guia).
  • Medições do navegador — a segunda tabela usa a API de Navigation Timing do próprio browser: MDN, “Navigation Timing”.
